# Network Visibility — Baseline Flow Pipeline (design)

Design for the **baseline** network-visibility path described in `plan.md` §8: kernel
`pflow(4)` export → a Go IPFIX collector → SQLite → a native flow UI, with a small nDPI
helper process for app-layer identification. This is the always-on summary that ships in
the base image. The **power tier** (ntopng + Redis) is a separate, opt-in deep-dive and is
out of scope here except where the two share UI.

## 1. Current state

Already built (and correct, but it is the **power tier**, not the baseline):

- `config.Visibility` — enabled / monitored-interfaces / HTTP port
- `render/ntopng.go` — generates `ntopng.conf` (Redis-less community mode)
- `server/visibility.go` — reverse-proxies ntopng under `/visibility/app` behind the
  WebUI session (appliance auth is the single front door)
- `web/templates/pages/visibility.html` — settings form + ntopng iframe

The `traffic` package is unrelated: it samples per-interface **throughput** (bytes/sec)
into a ring buffer for the Traffic Graph (§7). It is not flow data.

**Missing — everything in this document:** `pflow(4)` export, the Go IPFIX collector, the
flow database, the nDPI helper, and the native flow UI. The baseline has not been started.

## 2. Architecture

```
 pf state table
      │  (kernel, zero userland)
   pflow(4) ──IPFIX/UDP──▶ Go collector ──▶ flows.db (SQLite)
                          (internal/flow)        │
   nDPI helper ──app labels──▶ (join 5-tuple)    ▼
   (separate proc,                          native Flows UI
    libpcap, flow heads)                    (uPlot + htmx, fwd-served)
```

Two observers with a deliberate split of labor — this is why the baseline keeps **both**
`pflow` and an nDPI helper rather than one packet-capture path:

- **`pflow(4)`** is the kernel exporting the pf state table as flow records. It is the
  authoritative **byte/packet accounting** source: it sees all north-south and
  inter-segment traffic that pf tracks, with **zero userland packet copy**. It cannot
  classify applications — it never sees payload.
- **nDPI helper** is the only component that touches packets, and only the **first ~5–10
  packets of each flow** — DPI reaches a verdict quickly, then stops inspecting that flow.
  It emits `{5-tuple → app-label}` enrichment records. It does *not* do byte accounting
  (counting every byte in userland is exactly the line-rate cost `pflow` avoids).

The collector joins the two streams on 5-tuple + ifindex: `pflow` supplies the counts,
the helper supplies the app name.

## 3. Components

| Piece | Location | Responsibility |
|---|---|---|
| pflow config | `render/pflow.go` (new) | Render `pflow(4)` setup — `flowdst 127.0.0.1:<port>`, `pflowproto 10` (IPFIX), active/inactive timeouts. Generated by the §7 declarative engine, applied through the root helper. |
| IPFIX collector | `internal/flow` (new pkg) | UDP listener + IPFIX / NetFlow-v9 template decoder. Owns `flows.db`. Reimplemented in Go (goflow2 is the reference) — easy, drops a dependency. Runs **in-process** in fwd, like the `traffic` sampler. |
| nDPI helper | `cmd/ndpi-helper` (new, separate binary) | Links `libnDPI`. **Separate process, never cgo** — keeps LGPL out of the fwd binary (`plan.md` §8 hard rule). Streams app-label enrichment to the collector over a unix socket. fwd spawns and supervises it. |
| native Flows UI | `server` + new template | Top talkers, top apps, per-host breakdown, flow log. Server-rendered htmx + uPlot, served by fwd. |

**In-process vs separate:** the collector stays in-process (a goroutine in fwd) — it is
pure Go with no licensing constraint and mirrors the existing `traffic` sampler. Only the
nDPI helper must be a separate process, for the LGPL boundary.

## 4. Data model

Follow the existing `traffic` / `logs` stores: a single writer connection, WAL mode, and
age-bounded retention trimming.

- **Raw flows** — `ts, src, dst, sport, dport, proto, bytes, pkts, iface, app`
  (`app` nullable until the nDPI helper lands). Short retention (~1 hour); raw flow data
  is high-volume.
- **Rollups** — a timer pre-aggregates raw into per-minute and per-hour summaries
  (top talkers, per-app totals, per-host totals) for the day/week/month views, exactly the
  bucketing pattern the `traffic` store already uses.

Never query raw for long windows — query the rollups.

## 5. UI tiering

The two tiers share the Visibility page:

- **Baseline (default, always-on):** the native Flows view, served by fwd from the Go
  collector. No Redis, no ntopng, no GPLv3 app in the base image.
- **Power tier (opt-in):** the existing ntopng iframe, gated behind the power-tier
  packages being installed and enabled.

So `visibility.html`'s current ntopng iframe becomes the *power-tier* panel; the native
baseline view is what renders when ntopng is off. Split `config.Visibility` into a
lightweight `flow` block (baseline toggle, monitored interfaces) and the existing ntopng
block.

## 6. Build phasing

1. **`pflow` → collector → SQLite → native top-talkers UI**, `app` column empty. Flow
   volume and who-talks-to-whom work immediately — pure Go + kernel, no C dependency.
   Biggest value for least risk; ship this first.
2. **nDPI helper** — adds app names onto flows. Separate binary with its own build; the
   only C dependency at baseline.
3. **ntopng power tier** — already built; just re-gate it as opt-in.

## 7. Open questions

- **pflow granularity** — `pflow(4)` exports the whole pf state table, not per-interface.
  Per-interface filtering is therefore a collector-side concern via ifindex (or skipped at
  baseline). Confirm the FreeBSD `pflow(4)` IPFIX template actually carries ifindex.
- **Active-timeout latency** — long-lived flows only report on state expiry / active
  timeout, so the view is near-real-time, not per-packet. Pick a sane active timeout.
- **nDPI capture source** — libpcap vs netmap, and whether the helper sniffs the
  interfaces directly or reads a pf divert. Drives the helper's CPU cost.
- **Helper packaging** — `libnDPI` is LGPL; ship the helper as a base-image package built
  in the OS pipeline, linked dynamically, never static-linked into fwd.
